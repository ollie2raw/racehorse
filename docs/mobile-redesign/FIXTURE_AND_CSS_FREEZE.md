# Deterministic fixture, CSS ownership, and breakpoint freeze

## Screenshot fixture contract

One Playwright `mobile-landscape-visual` project renders **real route components and hooks** at fixed date `2026-09-25T12:00:00-07:00`, timezone `America/Los_Angeles`, DPR 1, reduced motion, fixed fonts, a fresh browser context per state, and localStorage welcome dismissal. `page.clock.install` (or equivalent before app boot) freezes display time; server date-keyed responses use the same fixture date. Fixture JSON is versioned under future `client/e2e/fixtures/mobile/`; per-test API intercepts are registered **before navigation**. Each fixture declares `stateId`, auth principal, API responses, optional socket script, local persistence seed, and expected visible selectors. A missing intercept fails the test; no live fallback. Fixture IDs are test-only, never product defaults.

The Home fixture asserts a visible five-item bar in **Multiplayer / Single Player / Tournament / Social / Learn** order with no `aria-current="page"` tab. A Multiplayer hub fixture asserts Multiplayer selected. No Home-only sixth tab or header Multiplayer action is part of the fixture contract.

**Auth seam:** Existing `.auth/daily-fritz-qa.json` is expiring and local-only, so it cannot own CI screenshot baselines. Existing dev-only `readE2eDevAuth` (`client/src/auth/e2eDevAuth.ts`) can create a stable user, but `useAuth.ts` currently gives that user only a username, and `GlobalNav` gets friends through Supabase `friendsApi.ts`. PR 0 adds a narrowly guarded, nonproduction fixture adapter for profile/rating and friends under the existing E2E dev-auth branch; it must be disabled in production builds and not change live auth. API-dependent data remains intercepted at network boundaries. Integration journeys using real server authority retain their separate QA fixture/tests.

## Canonical breakpoint policy

The single design policy is **wide shell iff viewport width ≥769 CSS px AND viewport height ≥600 CSS px**. Every other viewport is compact shell, including 844×390, 932×430, 390×844 and short desktop windows. This deliberately preserves the existing Tailwind `desk:` condition. Short-landscape density is a cross-cutting modifier at `orientation: landscape` and height ≤430 px; it does **not** select the shell by itself. The six requested viewports all use compact shell. Tall/narrow compact surfaces remain portrait capable.

PR 1 creates `client/config/responsivePolicy.js` exporting `WIDE_SHELL_QUERY = '(min-width: 769px) and (min-height: 600px)'` and `SHORT_LANDSCAPE_QUERY = '(orientation: landscape) and (max-height: 430px)'`. `tailwind.config.js` imports the first for `desk.raw`. `postcss.config.js` imports both and runs a tiny first plugin that prepends `@custom-media --desk …` and `@custom-media --short-landscape …` from those constants to each CSS root **before** `postcss-custom-media`; `tokens.css` deletes its manually authored width-only `--desk`. Keep `postcss-global-data` only for unrelated aliases/tokens. Add an architecture test that checks the compiled query strings and verifies one compact phone and one desktop sample. `--phone` must stop deciding shell, navigation, app scroll and card geometry; retain only genuinely width-specific legacy rules until their owning PR replaces them. `--below-wide` remains an ordinary width-based content helper only, never shell classification. No new `md:` shell decisions. This is one imported policy with two compiled consumers.

The shell uses viewport geometry for nav/header selection; page layout uses bounded content height and grids; reusable cards use container queries for their own width. At height ≤430, secondary copy/art compresses before actions. At very narrow card containers, deliberate rail/scroll rules apply. Do not infer handset from `orientation`, user agent, or physical device label. The current mismatch is visible in `client/src/styles/tokens.css:244-246` (`--desk` width only), `client/tailwind.config.js` (`desk:` width+height), `client/src/styles/rh-mobile-chrome.css` (height-aware inline query) and `client/src/components/nav/AppBottomTabBar.tsx` (stale 768 constant). PR 1 aligns shell/nav rules, then page owners remove stale `--phone` layout overrides as their route migrates.
