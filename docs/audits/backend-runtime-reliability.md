## R0/R1 findings

No R0 demonstrated.

1. **R1, fixed — headers-only database deadlines.** `supabaseUtils.ts:supabaseFetch` cleared its abort timer before `response.text()`, including error bodies. Headers followed by a stalled body could hold single flight forever, or accumulate overlapping catch-up runs. The separate scheduled ladder helper had the same gap. Both now consume the body inside the deadline and release the timer afterward. Tests stall 200/503 bodies, observe timeout, then successfully make another read.
2. **R1, fixed — poison ranked games block later valid ratings.** `periodService.ts:processRatingPeriod` eagerly rejected the whole user's opponent lookup; one deleted/missing opponent made every other pending game for that user wait indefinitely. Catch-up scanned users, then refetched their pending games, with no single flight and a 100,000-row up-front cohort. It now takes one 100-game chronological projection, reuses it, isolates row failures, caches failed opponent lookups, rotates its cursor, and backs off failed rows. Infrastructure failures still abort, not become row skips. Normal foreground error semantics and per-user opponent snapshots are retained; Glicko equations and atomic commit RPC are unchanged.
3. **R1, fixed — truncated restart hydration / stale rematch tails.** `roomLivePersistence.ts:attachLogEntries` read every entry in one implicit-cap response. 1200 moves produce 2400 combined events/move-log entries: with a 1000 response cap, valid snapshot hydration failed. A large prior-match tail also hid current streams. New keyset pages filter declared stream lengths before paging; malformed counts fail closed. Regression recovers all 2400 entries in 5 reads and a short rematch in 1.
4. **R1, fixed — cleanup destroys a room rejoined during archive await.** `roomSession.ts:scheduleRoomCleanup` checked sockets only before a database await. Returning players were then removed from memory and their live snapshot terminalized/deleted. Archive guard and post-await identity/socket checks protect the retained room; a reconnect during terminal write/delete restores its live snapshot before returning. Tests cover memory retention and both persistence await boundaries.
5. **R1, fixed — match-start retry could reject an already committed match.** `matchmaking/persistence.ts:recordMatchStart` retried a bare INSERT with the same PK. If first INSERT committed but response timed out, every retry got duplicate-key and matching gave up despite a durable row. Stable-ID insert now uses `on_conflict=id`/ignore-duplicates, never merges a later state. Lost-response test returns the same one row on attempt 2; genuine outage still stops at 4 attempts.
6. **R1, unresolved; schema decision required — lost forfeit metadata.** `multiplayer/roomForfeit.ts` passes `ratingScale=0.5` for `disconnect_timeout` only to inline rating computation. `ranking/rankedGamePayload.ts` has no persisted scale field. A pending game after inline failure/restart is later committed by `periodService.ts` with scale 1. Diagnostic `ranking/forfeitRecoveryMetadata.test.ts` uses identical profiles/scores/outcome: recovered delta is exactly twice the inline delta. Additionally, authoritative loss/win is only persisted when `RANKED_GAMES_OUTCOME_COLUMN_ENABLED=true`; if OFF, catch-up can invert a quitter's result when they were ahead. Actual production flag was not inspected. Cannot safely reconstruct historical scale/reason from a scoreline or invent it from log availability. No migration or policy change created.

## R2 findings / remediation

- Ranking overlap: catch-up single flight is now in the service (also covers admin/weekly callers); weekly decay has a separate in-process guard. Atomic RPCs already protected game application; the new guards bound redundant work and prevent concurrent no-op RD decays from inserting duplicate period records when numeric RD is unchanged.
- Daily Fritz failed-complete attempts formerly refetched/journaled every cadence indefinitely; now bounded process-local exponential backoff. Its ordinary incomplete/ambiguous 1-scan/0-individual-read contract remains unchanged. Finalization infrastructure outage now stops after the first failed individual lookup rather than walking all 100 and writing failure events.
- Weekly decay profile scan uses keysets rather than offset over a predicate concurrently cleared by gameplay. Summary now counts actual successful decay commits rather than all zero-game returns, including conflicts. Infrastructure outages stop the run.
- Bulk retention remains two unbounded affected-row DELETEs. No full JSON is returned and each network request has a 15s deadline. A strict DB work cap should use an indexed bounded-delete RPC if retention volume warrants it; no migration introduced.
- Failed detached reservation terminal PATCH has no durable retry ownership; restart also loses tracked reservations. Account-authorized shell restoration is on demand. A durable expiration/cleanup policy for lingering matchmaking rows is deferred, not concealed as a running reconciliation worker.

## Data access / concurrency / retries

A projected ranking page still requires player/opponent profiles and atomic writes: those reads are inputs and the RPC writes are actual work, not the old incomplete-attempt amplification. For 100 separate Fritz players, the redundant 100 pending-game reads disappear (301→201 calls). Same-player opponents are sampled once before that user's games; successful/failed duplicate lookups are cached inside the page. Pagination is deterministic; scan failures retain cursors. Per-process retry caches are capped and reset on restart, so the first boot may revisit poison rows but processes at most 100 candidates. No status change closes a potentially resumable Daily Fritz row.

Rating and Ghost application remain database-idempotent using receipts/row locks/source keys. Foreground rating winning a race returns `ranked_already_processed`; catch-up rereads current profile and reports no new application. Matchmaking first-terminal-writer filter remains intact. No distributed locking added.

## Observability / lifecycle

Ranking summaries cover duration, scanned, processed, failed, skipped/unprocessed, keyset continuation, outcome, and overlap. Error arrays in catch-up logging are sampled to five with full count. Fritz summaries include zero-work runs, duration, page continuation, failure/backoff counts and overlap. Decay reports scanned/pages/actual applied count, failure/abort and duration. No new per-row success stream or monitoring platform.

Shutdown already rejects new sockets, drains tournament orchestration when active, stops new debounced room writes, flushes/awaits live persistence (10s ceiling), closes sockets and exits. Ranking/Fritz/warmup/retention timers are not explicitly drained or cancelled by that shutdown hook; their atomic/idempotent state survives interruption, while local cursors/backoff reset. Review, if enabled, resumes via durable expired lease/backoff; search work is bounded off-thread. This pass does not claim a comprehensive drain of detached Ghost/async-verification work. Such shutdown ownership remains a material operational follow-up; it must avoid blocking HTTP shutdown indefinitely or making incomplete evidence authoritative.

## Deferred schema/policy items

The forfeit R1 blocks a READY verdict. The separate design is [backend-runtime-forfeit-metadata-proposal.md](backend-runtime-forfeit-metadata-proposal.md). A separate proposed migration/design must persist rating multiplier and authoritative outcome at ranked-game insertion, bind them to source identity, and apply exactly that stored policy in inline and catch-up paths. Decide how existing ambiguous pending forfeits are handled; do not automatically reinterpret or reconcile them. Verify outcome-column deployment/flag through a separately authorized operation. Add equality tests across inline, failed-inline, restart, and duplicate application before integration.

Optional indexes: partial `(played_at,id)` on pending ranked games, and an appropriate inactivity scan index on profiles. Existing player/date indexes and new bounded requests are sufficient for local correctness tests; no production plan/EXPLAIN was accessed. Durable retry quarantine, strict retention-delete caps, and shutdown drains need their own narrowly scoped persistence/lifecycle decision. Tournaments stay OFF. No R3 work.
