# Daily Fritz post-game review: design (2026-11-02)

Goal: a player who finishes a Daily Fritz game can open the same review they get after Play vs Fritz and multiplayer. Today they get none. The owner approved starting this; the choices below are mine ("think like chess.com").

## What exists today (checked in the code)

- **Review is deliberately off for Daily Fritz.** `postGameReviewPolicy.ts` says Daily Fritz is "structurally excluded", and live snapshot capture excludes it "so DF verification payloads stay untouched". That second reason is the real constraint: Daily Fritz verification has been the most fragile system in the app (503 strandings in 18 days before the engine journal fix), so nothing in live play may change.
- **The server keeps only a digest.** For every hand it verifies, the server stores a summary and a sha256 of the transcript (`VerifiedDailyFritzHandRecord`: scores before and after, winner, `actionCount`, `transcriptDigest`). It does **not** keep the actions. A finished Daily Fritz game therefore cannot be reconstructed later.
- **The server does see the full actions, once.** `verifyDailyFritzHand` receives the whole transcript (`actions`, each with actor, kind, tile, position) and replays it against the official state built from the published challenge. The deal is deterministic from the challenge and hand index (`createOfficialDailyFritzHandState`), so actions plus challenge are enough to rebuild a hand.
- **The saved-game plumbing exists.** `game_records` (modes `pvf`, `mp`), list and read endpoints, a saved-game reopen screen, and a review that runs from a rebuilt game (`SavedGameReview`) are all in place from the multiplayer work.

## Decision

Build the Daily Fritz review **from what the server has already verified**, as a best-effort side effect after verification succeeds, and open it from the saved-games list. **Live Daily Fritz play, capture and verification do not change at all.** A hand that does not replay exactly is simply "review unavailable for this hand"; it never affects scoring, the leaderboard or the run.

Why this and not the alternatives:

| Option | Verdict |
| --- | --- |
| Capture review snapshots during live Daily Fritz play, like Play vs Fritz | **Rejected.** Touches the fragile live path; the code comment says to keep it untouched. |
| Review locally on the finished-set card from the client's own journal | **Rejected.** Client-asserted, lost on reload or another device, and nothing to reopen from the Games list (chess.com keeps every game). |
| Save the game on the server from the verified transcripts, review derives from the saved game | **Chosen.** Server-authoritative, reopenable anywhere, same model as multiplayer, no change to live play. |

## Plan: one PR each, in order

1. **DF-1 (server, no SQL): a hand replay. DONE, with one deliberate change from the plan above.** A function that turns a verified transcript plus the official initial state into the ordered engine steps (state before, command, state after): `replayVerifiedDailyFritzHand` in `server/src/dailyFritzHandReplay.ts`. **Change:** the plan said "strict, unavailable for anything the verifier had to tolerate". Re-implementing the verifier's tolerance would have been a second copy of the most fragile code in the app, so instead `verifyDailyFritzHand` gained one optional, read-only observer (`onStep`) that reports every engine command it applies, including the two kinds it infers for a degraded client (an omitted mandatory draw, an omitted official Fritz turn). Those really happened in the official game, so a replay needs them. They are flagged (`origin: 'inferred-draw' | 'recovered-fritz'`, `inferredStepCount`), and the replay re-applies the steps and requires the terminal state to equal the verifier's own. The observer's errors are swallowed and a test proves the verifier returns the identical result with no observer, a quiet one and a throwing one. **Evidence:** on the real client pipeline (the fidelity test's simulated hands, 100 seeds by 4 hands) every cleanly observed hand replays with nothing inferred, from the move log and from the journal, and with the journal under 35% observation loss every hand still replays; seven new unit tests also cover both inferred shapes and the rejected shapes (the verifier's own code comes back, nothing throws). Mutation-checked (dropping inferred draws, and letting observer errors propagate, each fail tests). **Not measurable yet:** how often REAL production hands need inferred steps, because the server has never kept transcripts. DF-2 starts keeping them, and DF-3 will count `inferredStepCount` per saved game.
2. **DF-2 (server + SQL for the owner): keep the verified transcripts. WRITTEN, waiting for the owner to apply the SQL.** `supabase/migrations/2026-11-02_daily_fritz_hand_records.sql` creates `daily_fritz_hand_records` (user, attempt, challenge, game, hand, transcript digest, versions, action count, the transcript JSON). `server/src/dailyFritzHandRecords.ts` builds a row from a verified hand and inserts it in the background. **Where it hooks:** `attemptVerifyHand`, the one function all three routes (next-hand, record-game, async record-game) verify through, after a hand verifies, wrapped so a failure cannot reach the caller; behind `DF_HAND_RECORDS_ENABLED` (off by default, must not be set before the SQL is applied). **Two changes from the first sketch:** (1) the row is keyed by the transcript digest too, because a hand can verify more than once (a retried request) and only the version written to the attempt's ledger is authoritative; the ledger already records that digest per hand, so DF-3 selects the row that matches it. An identical retry is a no-op, different evidence is a second row the ledger never points at. (2) no foreign key to the attempts table (a record can be written before that row is final); it cascades from the account only. **Safe by construction:** the row is built by re-deriving the transcript digest and requiring it to equal the verifier's own, refuses non-UUID ids, an oversized transcript or a receipt for another hand, and every failure (table missing, bad data, insert error) is logged (at most once a minute) and swallowed. Clients have no access (RLS on, all client operations denied). **SQL verified on a scratch Postgres 16:** applies twice, valid insert, identical retry is a no-op, five bad rows rejected by the right constraint, an owner's client sees 0 rows and cannot insert, update or delete (policy proven with grants in place, as on Supabase), rows go with the account, rollback drops cleanly.
3. **DF-3 (server, no SQL): derive a game record. CHANGED from the sketch above, in two parts.** *Why changed:* writing a `game_records` row when a game ends means hooking the record-game route's game-end path (idempotent retries, transactional commands, an async variant), the most fragile code in the app, and racing the last hand's background insert. Deriving the record **when it is asked for** needs none of that: no write path, no race, no second SQL change, no flag, and no change to any existing Daily Fritz route.
   - **DF-3a (done): the builder.** `server/src/gameRecords/dailyFritzGameRecord.ts` turns a game's DF-1 hand replays into a record in the **multiplayer record format** (players "you" and "opponent"; the opponent is Fritz). Reusing that format means the server's pure replay (`replayMultiplayerRecord`), the client's rebuild (`rebuildMultiplayerGameFromRecord`) and the saved-game review work on it unchanged. Two bridges: Daily Fritz logs each draw as a command while the multiplayer format logs "draw until a play exists" as one action (so a run of draws folds into one DRAW and the tiles drawn are read off the boneyard before and after each command); and Daily Fritz logs every pass while the multiplayer format does not log forced ones (a pass is only legal with no play and no draw, so every pass is forced, and replaying a logged one is refused as out of turn; found by the first test run). **Evidence:** 16 simulated full games (both starters, 7 and 14 tile deals) each replay through the multiplayer format's own server replay to the same hand scores, final scores and winner, AND rebuild through the CLIENT engine to the same scores (21 cross-engine checks); a game with a lost draw observation still builds, with the inferred step counted; the record carries no account, attempt or challenge id and only the seat names "you" and "opponent"; mutation-checked (no draw folding, no drawn tiles, keeping passes each fail 3 tests).
   - **DF-3b (done): the read side.** Two owner-only GETs, registered from a new `dailyFritzGameRecordRoute.ts` (the existing Daily Fritz routes are untouched, `dailyFritz.ts` gains two lines): `/api/daily-fritz/games` lists the player's verified games (newest first, each marked `reviewable` when every hand the ledger names is stored; unverified games are not listed) and `/api/daily-fritz/game-record?attempt_id=&game_number=` returns one game in full or says why it cannot (404 with a `reason`). The derivation (`server/src/dailyFritzSavedGame.ts`) takes the hands the **ledger** names by digest (a hand verified twice may have two stored rows; only the ledger's digest counts), rebuilds each hand's starting state with `buildHandVerificationInput`, **extracted unchanged from `verifyAttemptHand`** so the review uses exactly the inputs verification used (the 254 existing route tests pass unchanged), replays it through the verifier (DF-1), builds the record (DF-3a), requires it to replay through the multiplayer format's own pure replay, and requires its scores to equal the **ledger's** verified scores. Every refusal is a reason, never a guess: `game_not_verified`, `missing_hand_record:N`, `hand_not_replayable:N:code` (including attempt-level refusals such as a retired policy, which throw before the verifier runs), `record_does_not_replay`, `ledger_score_mismatch`. Someone else's attempt id reads as not found; a failure answers a fixed sentence in production. **Evidence:** 9 service tests on whole games driven through the real `attemptVerifyHand` and the real ledger writers (two games, both draw winners), 7 HTTP tests; mutation-checked (picking a row by hand index instead of digest, skipping the ledger score check, scoping the lookup to the wrong user each fail tests).
4. **DF-4 (client): rebuild and review. DONE (this PR).** `loadSavedGame` now understands a `dfz:<attempt id>:<game>` id: it fetches `GET /api/daily-fritz/game-record`, reads the response with `parseSavedDailyFritzGame`, and rebuilds it with the **unchanged** multiplayer rebuild, so the saved-game review opens it like any other game. Only the labels differ: the mode reads "Daily Fritz", the opponent "Fritz", and the review grades at the tier Fritz played (the response now carries `fritzTier`; a multiplayer game still uses the default tier). A 404 from the endpoint is its own failure, `not_reviewable`, with words a player can act on ("Daily Fritz games can be reviewed once their moves have been kept, so games played before that started are not available"), not "we can't find that game". **Evidence:** a real fixture generated by the server's own derivation (`fixtures/dailyFritzSavedGame.json`, a 4-hand game won 28-25); the id parser, the loader (right endpoint, rebuilt scores equal the verified result, 404, outage, wrong mode, tampered action), labels, tier and copy are unit tested; and the **real pipeline** test (`SavedGameReview.dailyFritz.pipeline.test.tsx`: real rebuild, real review hook, real engine escalation, real analyzer and accuracy model, only the network stubbed) shows the server is sent only the player's decisions under the game's own id, the summary says Victory and Daily Fritz, the accuracy is a real percentage, and the finished review is saved under the same id. Mutation-checked (not routing `dfz:` ids, ignoring the tier). **Known, unchanged behavior:** the saved review's `mode` is written as `pvf` by the shared hook for every saved game, as it already is for saved multiplayer games; a review row is keyed by its `dfz:` id, and the label is the archive's job (DF-5). Original sketch: Rebuild the game from the record (as `rebuildMultiplayerGameFromRecord` does), reuse `SavedGameReview`; opponent label "Fritz", title "Daily Fritz, <date>, Game N".
5. **DF-5 (client): the entry points.** A "Review" button on the finished-set card and each game in the Games list. The set-final overlay is where the old comment said hand interstitials fight the prompt, so the button goes on the card the player already reaches, not into the interstitial.

## Risks and how each is held

- **A transcript that does not replay.** Handled by DF-1 returning `unavailable`, and DF-1's measured rate decides whether to continue.
- **Verification impact.** DF-2 runs after the response is decided, inside try/catch, behind a flag; a test asserts that a throwing store does not change the response.
- **Storage.** A hand is tens of actions; a full set is a few hundred small objects. Measured in DF-1.
- **Honesty.** Daily Fritz is played against Elite Fritz with a fixed deal; the review grades the player's moves against the same engine as every other review, with the second-opinion rule from #472.
